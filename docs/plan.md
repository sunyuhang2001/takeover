### 2.2 all927 的字段（从截图读出）

`dis_id, vin, disengage_time, dis_engage_time, position_time_sql, acceleration, acc_long, acc_lat, direction, drive_mode, latitude, longitude, velocity, altitude, acc_long_min, t2.acc…`（后面还有列，截图没截全）

- `disengage_time`：事件时刻，北京时间。同一事件内每行都一样。
- `dis_engage_time`：每一行的时刻，北京时间。名字容易误读，它**不是**事件时刻。
- `position_time_sql`：每一行的时刻，比 `dis_engage_time` 早 8 小时，应该是 UTC。
- `drive_mode`：1 表示自动驾驶，0 表示人工驾驶。样例里在事件时刻从 1 变成 0。
- 坐标大约在北纬 31.28°、东经 121.19°，即嘉定安亭汽车城一带。
- `acc_long_min` 等是事件级的字段，在每一行里重复出现。

### 2.3 前人的流程为什么只剩 35 条

1. **从清单出发找文件**：只搜了 0920 表里的 VIN 和时间，清单以外的视频根本没有进入统计。这是"很多视频被筛掉了"的主要原因。
2. **硬性条件太多**：要求三通道齐全，且 all927 里必须有经纬度。只有部分通道的事件、经纬度只在其他轨迹表里的事件，都被丢掉了。
3. **没有按事件聚合**：同一个片段在多个目录里有拷贝，同一个事件也可能有好几段视频，这些都没做去重和合并。
4. **没纳入路侧数据**：路侧 mp4 还混在匹配结果里（PPT 最后一页已经注意到这一点）。

### 2.4 已发现的数据问题

- **时区不一致**：`position_time_sql` 是 UTC，而视频文件名和事件清单用的是北京时间。
- **轨迹有重复、乱序**：在 all927 里，每个事件的 60 秒窗口内约有 120 行，但不同的秒只有约 60 个，而且时间不是按顺序排的。统计之前要先按"vin + 时刻"去重并排序。
- **文件有多份拷贝**：同一段视频或路侧片段，在 `VIDEO` 和各个 `video*` 目录之间、在 `anli`、`DOM`、`新建文件夹` 之间都有重复。

## 3. 总体思路：先盘资产，再建事件主表

不再从清单出发去找文件。先把每一类数据资产各自盘点清楚，再在"事件"这一层做关联：

```
全盘文件索引（只扫一次）
   ├─ 自车视频  → 解析 VIN / 通道 / 起止时间 → 去重 → 视频事件
   ├─ 表格目录  → 按列名分组 → 轨迹表 / 事件清单 / 路侧表
   ├─ 自车轨迹  → 统一时区、去重 → 每辆车的时间覆盖索引 + drive_mode 跳变点
   ├─ 原因清单  → 0920 表和其他清单
   └─ 路侧数据  → 路口 / 相机 / 时间窗，并与案例目录关联
                ↓
        事件主表：每行一个事件，带 4 个标志位
        V = 自车视频   T = 自车轨迹   R = 路侧数据   D = 原因描述
                ↓
        按 16 种组合分别计数 → 直接回答 Q1 / Q2
```

- **Q1** = V=1 且 T=1 的事件数。再按 D=1 / D=0 拆开（D=0 的就是要人工看视频的），再按通道完整度拆开（三通道、ch1+ch2、仅 ch3 等）。
- **Q2**：
  - 仅视频 = V=1 且 T=0；
  - 仅自车轨迹 = V=0、T=1、R=0；
  - 自车轨迹 + 路侧 = V=0、T=1、R=1；
  - 顺带统计：只有路侧数据的，以及只有原因描述的（清单里有这个事件，但哪种数据都找不到）。

### 3.1 统计口径（要写进报告；阈值是初稿，可以调）

| 概念 | 定义 |
|---|---|
| 事件 | 同一 VIN、时刻相差不超过 60 秒的记录，算同一个事件。事件时刻按优先级取：清单时间 > 轨迹中 drive_mode 从 1 变 0 的时刻 > 视频片段中点 |
| 有自车视频（V） | 至少有一个通道的视频片段覆盖事件时刻。同时记录通道组合和片段数 |
| 有自车轨迹（T） | 在事件时刻前后各 30 秒内，去重后带经纬度的秒数不少于 20。表里记录实际秒数，方便以后换阈值 |
| 有路侧（R） | 路侧片段与事件时间窗有重叠，并且满足以下任一条件：案例目录名里的 VIN 与事件一致，或事件位置在该路口附近 |
| 有原因（D） | 在 0920 表（或其他清单）里，该事件的原因或描述字段不为空 |

## 4. 在堡垒机上怎么干活

约束：堡垒机只能通过网页连接；剪贴板只能从本地往堡垒机粘，不能往回复制；堡垒机没有网络。

### 4.1 迭代循环

1. 我在仓库的 `bastion/` 里写好脚本并推送。
2. 你在本地打开脚本（GitHub 网页或本会话都行），复制后粘贴到堡垒机的 VS Code 或 PyCharm 里，保存并运行。
3. 每个脚本运行完会打印一屏摘要，你截图发给我。
4. 我读截图，调整规则，或者写下一步的脚本。

### 4.2 脚本约定

- 每个脚本是单个文件、能独立运行，只依赖堡垒机上已经装好的包（第 0 阶段确认有哪些）。
- **对原始数据只读**。所有输出都写到 `D:\takeover_audit\<步骤号>_<名称>\`，输出目录用英文名，避免编码问题。
- 明细结果写成 csv 或 xlsx，留在堡垒机上；控制台只打印聚合统计，每屏不超过约 40 行，方便截图。
- 脚本开头打印脚本名、版本号和自校验码（把换行统一成 LF 后算 md5，取前 8 位），结尾打印 `END`。这样能确认代码粘贴完整，也能看出跑的是哪个版本。
- 坏文件、读不了的表记到 `errors.csv`，不让整个脚本中断。
- 全盘扫描的结果缓存成 `file_index.csv`，后面的步骤都复用它，不重复扫盘。

### 4.3 数据安全

从堡垒机带出来的只有聚合数字。VIN 明细和坐标明细不出堡垒机；截图里如果有 VIN，也不要提交到仓库。

## 5. 分阶段计划

### 阶段 0：环境探查和交接材料（`00_probe.py`）

- 脚本打印以下信息：
  - Python 版本；
  - pandas、openpyxl、xlrd、numpy、cv2、matplotlib 是否可用；
  - 各盘的容量和内存大小；
  - D 盘的一级目录清单。
- 测试粘贴通道：脚本里带中文和多层缩进，运行后比对自校验码，看中文会不会乱码、代码会不会被截断。
- 另外请你截图以下交接材料：
  - `D:\堡垒机数据筛选\README.md` 和代码目录；
  - `video_audit_output` 和 `RoadsideData` 的一级目录结构；
  - 0920 表的表头和前几行（VIN 可以打码）。

### 阶段 1：全盘文件索引（`01_scan_files.py`）

- 遍历所有本地盘，跳过系统目录、程序目录、回收站、miniconda 等。每个文件记录路径、扩展名、大小和修改时间，写入 `file_index.csv`。
- 摘要统计：
  - 按"一级目录 × 扩展名"统计文件数和 GB；
  - 视频类（avi、mp4、mkv、h264 等）、表格类（xlsx、xls、csv）、其他数据类（json、db、sql、mat、pcd、bag、zip 等）各有多少。
- 按命名规则识别哪些是车载视频、哪些是路侧视频。**命名对不上任何规则的视频单独列出来**，由人工判断。

### 阶段 2：分资产解析

- **2a 自车视频（`02_ego_video.py`）**
  - 从路径里解析出 VIN（17 位）、通道、起止时间、时长和大小。
  - 同一 VIN、同一通道、起止时间相同的文件，算作同一个片段，记录它有几份副本、各份大小是否一致。
  - 同一 VIN 下时间相近的片段，聚合成一个"视频事件"。
  - 对清单里已有的事件，统计"片段中点 − 清单时间"的分布。正常应集中在 0 秒；如果出现 ±8 小时，说明有片段是按 UTC 命名的。
  - 体积过小的文件标记为可疑。如果装了 cv2，就抽样读取帧数、fps 和分辨率。
  - 产出：片段数、视频事件数、车辆数、时间范围、按月分布、通道完整度、总 GB。
- **2b 表格目录和字段（`03_table_catalog.py`）**
  - 所有 xlsx、xls、csv 文件，每个 sheet 只读表头和前几行，并记录行数和编码。
  - 按"列名组合"分组，结构相同的文件归为一组。
  - 自动归类为三种：
    - 轨迹表：同时有 vin、时间和经纬度；
    - 事件清单：同时有 vin、时间和描述；
    - 路侧表：有目标 ID、类型、坐标等列。
  - 报告里"字段名"那一节就从这里来。
- **2c 自车轨迹（`04_trajectory_index.py`）**
  - 对每张轨迹表：通过列与列之间的时间比对，判断是否有 8 小时偏移，从而推断时区；然后按"vin + 时刻"去重并排序。
  - 为每辆车（或每个事件切片）输出：时间覆盖段、行数、采样间隔、经纬度有效率和坐标范围（bbox）。
  - 找出 drive_mode 从 1 变 0 的时刻，用来发现清单以外的事件，也用来校准时间。
  - 输出字段字典：字段名、类型、示例值、缺失率。
- **2d 原因清单（`05_event_lists.py`）**
  - 统计 0920 表，以及 2b 里新发现的其他清单：条数、VIN 数、时间范围、原因字段的填写率、原因类别分布、重复记录。
- **2e 路侧数据（`06_roadside.py`）**
  - 路侧视频：解析相机编号、路口、方位和起止时间；从案例目录名里取出 VIN 和时间；去掉跨目录的重复拷贝。
  - `RoadsideData` 等目录：先截图看结构，再决定怎么解析。如果里面有目标级数据，就统计字段、时间范围和覆盖了哪些路口。

### 阶段 3：事件主表和覆盖统计（`07_event_master.py`）

- 事件全集包括：0920 清单里的事件、从视频推断的事件、从轨迹切片和 drive_mode 跳变找到的事件、路侧案例对应的事件。按第 3.1 节的口径合并，合并时有冲突的单独列出来。
- 产出：
  - `事件主表.xlsx`：每行一个事件，包括 V/T/R/D 标志、通道组合、轨迹覆盖秒数、各类文件的路径（做成超链接），以及是否属于前人的 35 条。
  - V/T/R/D 的 16 种组合计数表。
  - 与前人 35 条的对账漏斗：清单事件 → 有任一视频 → 三通道齐全 → all927 有经纬度 → 35。同时核对这 35 条是否都能在新结果里找到。
- 需要回传的截图：组合计数表和漏斗。这一步做完，Q1 和 Q2 的数字就有了。

### 阶段 4：抽样核验，准备人工标注（`08_qc_annotation.py`）

- 每种组合随机抽 5～10 个事件，人工打开视频和轨迹核对：
  - VIN 对不对；
  - 视频里看到的接管时刻、drive_mode 的跳变时刻、清单时间，这三者能不能对上；
  - 视频能不能播放，画面是否正常。
- 发现问题就修改规则，重跑阶段 3。
- 生成《无原因事件人工标注表》：
  - 预先填好的列：事件 ID、VIN、时间、ch1/ch2/ch3 的超链接、轨迹、路侧视频；
  - 留空待填的列：原因类别、描述、场景要素、能否在模拟器复现、标注人。
- 按每条约 2 分钟估算人工工作量。

### 阶段 5：写报告

- 数字从截图里整理出来；图表用聚合数字在仓库这边画，不带出明细。
- 大纲见第 6 节。

## 6. 数据情况报告大纲

1. **结论摘要（一页）**：事件总数；Q1、Q2 的数字；和前人 35 条相比差在哪里、为什么。
2. **口径说明**：事件和 V/T/R/D 各自的定义与阈值。
3. **数据资产总览表**：列为 资产 / 位置 / 文件数和体量 / 记录数 / 车辆数 / 时间范围 / 空间范围 / 关键字段。
4. **各类资产详述**：
   - 自车视频：命名规则、通道、时长；
   - 自车轨迹：字段字典、采样率、时区；
   - 路侧数据：路口和相机清单、时间范围；
   - 原因清单：填写率、原因类别分布。
5. **事件级覆盖情况**：16 种组合的计数、通道完整度、按月和按车辆的分布、空间分布（按路口或网格计数）。
6. **与前人筛选结果的对账漏斗**。
7. **数据质量问题和对应的处理规则**。
8. **下一步**：
   - 人工标注计划；
   - 模拟器复现候选清单，按数据丰富程度排序（视频、轨迹、路侧三样都有的排最前）；
   - 需要补采的数据。
9. **附录**：目录清单、字段字典、各脚本版本。
